## 0. 结论速览

当前系统已打通「线路 product 化 → C 端浏览/报名/电商下单 → 后端成团/计调/收款/核算」的**纵向闭环**，但存在三个结构性短板，本设计聚焦补齐：

| 短板 | 现状 | 本设计动作 |
|------|------|-----------|
| **C 端只有"下单"，没有"下单后"** | 有浏览/报名/回执，缺查询/补录/退改签/提醒 | 新增「游客订单中心」统一承接下单后全生命周期 |
| **成团是"人工开关"，无业务规则** | 首个下单自动建 draft 团，计调手动确认；无成团阈值、无未成团退款 | 引入 `min_seats` 成团阈值 + 未成团自动退款/取消 |
| **余位只增不减** | 报名 `booked_seats += N` 单向递增，退订不释放余位 | 退订/取消/改签统一走「余位释放」原子操作 |

**设计原则（三条硬约束，贯穿全文）**：

1. **单一事实源**：余位唯一源 = `tour.departure.booked_seats`；金额唯一源 = `tour.plan`（`_sync_amounts_from_regs` 幂等汇总 + 收款回写）；人数唯一源 = `tour.plan`。任何新功能不得另起炉灶。
2. **财务唯一口径在 tour.plan**：`sale.order` 只做销售/收款入口，不独立出账（保留现有决策，后续所有 C 端能力同样遵守）。
3. **游客侧状态是"后端状态的投影"，不是新状态机**：C 端只读映射，所有状态流转仍发生在 `tour.plan` / `tour.plan.reg` / `tour.payment.claim`。

## 2. C 端游客自助全流程

### 2.1 总流程图

```
游客入口（官网）
    │
    ├─ 1. 浏览线路  /tours（分类/关键字/起价/天数）
    ├─ 2. 线路详情  /tours/<line_id>（行程/费用/班期余位/五档价）
    ├─ 3. 选班期 + 填人数
    │       ├─ 轻量报名（无登录）→ create_online_reg
    │       └─ 电商下单（加购）→ sale.order 确认 → 桥接
    ├─ 4. 支付（P0 微信在线收银台 + 线下付款兜底）
    ├─ 5. 证件补录（P1，出团前 N 天截止）
    ├─ 6. 订单/报名查询（P0，凭单号+手机号，或登录会员中心）
    ├─ 7. 改签退订（P0，C 端提交申请，后端审批）
    └─ 8. 出团前提醒（P1，短信/邮件）
```

### 2.2 各步骤页面 / 状态 / 规则

#### 2.2.1 浏览线路（已实现，保留）

- 页面：`/tours` 列表、`/tours/<line_id>` 详情
- 可见性：`active=True` 且 `audit_state='approved'` 的线路；`state='published'` 且 `remain_seats>0` 且 `start_date≥今天` 的班期可选
- 起价 = 该线路已发布未过期班期最低成人价（无则线路成人价；均无显示「价格电询」）

#### 2.2.2 报名 / 下单（已实现，保留，仅微调）

- 两条入口共用 `_create_plan_reg_from_order`，保证校验/计价/建团/回写/汇总只有一套逻辑
- 校验顺序（已实现）：线路/班期匹配 → 班期已发布 → 未过期 → 有余位 → 人数≥1 → 人数≤余位 → 联系人 → 手机（轻量报名强制 11 位）→ 逐人证件
- **微调**：报名成功页从"静态回执"升级为"订单中心入口"，展示**游客侧状态徽标**（见 §5 映射表）+ 后续动作按钮（补录证件 / 查进度 / 退改签）

#### 2.2.3 支付（P0 微信在线收银台 + 线下兜底）

| 档位 | 内容 | 规则 |
|------|------|------|
| **P0（新增）** | **微信支付**在线收银台（本期唯一在线渠道），接 Odoo payment provider（wechat） | 支付回调 → 自动生成 tour.payment.claim（pay_channel=wechat，supplier_id 关联游客 partner）→ 走既有审核流程；退款**原路退回**；**不得**在 sale.order 上独立确认收入 |
| **P0（保留）** | 线下付款：回执页展示应付金额 + 收款账户 + 到店地址 + 客服电话 | 付款后走 tour.payment.claim 认领，`sum_pay_normal` 回写；在线支付失败/超时自动回落此档 |
| **P1（跟进）** | 支付宝在线收银台 | 复用微信同一条接入层与落账路径（仅 provider 不同） |
| **P2（不做）** | 银联/银行卡 | 散客自助报名场景占比极低，本期不投入 |

> 在线支付的关键约束：`sale.order` 的支付只作为「收款触发源」，落账仍归 `tour.payment.claim` → `tour.plan`。避免出现 sale.order 一套账、tour.plan 一套账的双口径。

#### 2.2.4 证件补录（G5，P1 新增）

- **为什么需要**：电商下单桥接 `passengers=None`（结账流程无法逐人录证件）；轻量报名虽能逐人填，但允许"先报后补"更符合实际（客人未必当场带齐证件）
- **规则**：
  - 出团前 **7 天（可配置 `tour_website.id_deadline_days`）** 为补录截止
  - 未补全的报名单：出团前 3 天系统预警 + 短信提醒（P2 依赖短信网关）；截止后仍未补全，后台标记 `id_incomplete=True`，计调出团前置校验可拦截（可配置）
  - 补录入口：订单中心 → 「补录证件」→ 逐人填写（复用 `tour.plan.reg.passenger`），仅本人（单号+手机号校验）可补
- **数据落地**：仍写 `tour.plan.reg.passenger`，不新增模型；新增 `tour.plan.reg.id_complete`（computed：passenger 数 == guest_count 且全有 id_number）

#### 2.2.5 订单 / 报名查询（G1，P0 新增）

- **已拍板（D4）**：无登录查询（凭证 1）为默认入口，不强制注册登录；会员中心（凭证 2）为 P1 增值能力，两者并存、互不替代
- **两种查询凭证**（复用 BS-13 §7 隔离红线）：
  1. 无登录：`报名单号 reg_code + 联系人手机号`（手机号校验通过后展示）
  2. 登录会员：绑定 partner 后列表查看名下全部报名（P1 会员中心）
- **页面字段（游客侧只读投影）**：报名单号、线路、班期（出发/返回日期）、人数、应付金额、已收金额、**游客侧状态**（§5 映射）、下一动作提示、退改签按钮
- **隔离红线**：仅能查本人报名，严禁遍历他人（reg_code 非连续、手机号强校验、频率限制）

#### 2.2.6 改签 / 退订（G2，P0 新增）

**退订（取消报名）**：

- C 端提交退订申请 → 生成 `tour.plan.reg.cancel`（新增申请模型）→ 后端审批 → 释放余位 + 退款
- 退款按梯度扣费（见 §6.2）
- 审批通过后：`booked_seats -= N`（释放余位，G3）→ `sum_money_return` 累加 → 走退款流程（负数红冲或独立退款单，对齐 BS-02 §6.4）

**改签（换班期）**：

- 同一线路内换到另一 `tour.departure`：原班期释放余位 + 新班期占位 + 重新计价（快照）+ 生成 `tour.plan.change` 变更记录（复用 BS-02 §4.5 溯源机制）
- 改签后 `reg.plan_id` 指向新团（或同团不同班期），`first_plan_id` 语义不变

**状态**：申请模型状态机 `draft→submitted→approved/rejected`；审批人 = 销售/计调（按配置）

#### 2.2.7 出团前提醒（G7，P1 新增）

- 集合时间/地点、行程、证件/保险须知；出团前 1 天 + 当天两轮短信/邮件
- 依赖短信网关（P2），邮件可先行

### 2.3 游客侧状态机（投影，非新状态机）

见 §5 状态映射表。核心：游客只看到 5 个聚合态，全部由后端 `tour.plan.state` + `tour.plan.reg` + `tour.payment.claim.claim_state` 推导。

## 3. B 端后端管理全流程

### 3.1 总流程图（已实现，本设计补「成团阈值」与「退订承接」）

```
C 端报名/下单（tour.plan.reg，from_type 6/7）
    ↓
1. 订单确认（tour.plan：draft → pending → confirmed）
    ↓
2. 成团判断（新增：guest_count ≥ min_seats 才可 confirmed；
   未达阈值 → 待成团 / 超时未成团 → 自动取消 + 退款）
    ↓
3. 计调运营（tour.operation：导/车/房/餐/票 project.task，冲突检测，出团前置校验）
    ↓
4. 收款认领（tour.payment.claim：登记→认领到团→审核→平账，回写 sum_pay_normal）
    ↓
5. 单团核算（analytic 1:1，收入/成本/利润/差额征税/佣金）
    ↓
6. 佣金结算（tour.commission：导游/购物返佣）
    ↓
7. 游客服务（订单查询应答 + 退订审批 + 证件催补 + 投诉登记 P1）
```

### 3.2 各环节要点与新增

| 环节 | 现状 | 本设计新增/调整 |
|------|------|----------------|
| 1 订单确认 | `action_confirm` draft→pending→confirmed | 增加成团阈值前置校验（§6.1）：达阈值才可 confirmed |
| 2 成团 | 首个下单自动建 draft 团 | 增加 `min_seats` + 「待成团」判定 + 未成团超时取消退款 |
| 3 计调 | project.task booking | 不变；出团前置校验增加「证件补全」可选校验（§2.2.4） |
| 4 收款 | payment.claim | 在线支付自动生成 claim（P1）；退订退款走独立退款动作 |
| 5 核算 | analytic 1:1 | 不变 |
| 6 佣金 | tour.commission | 不变 |
| 7 游客服务 | 无 C 端承接 | 退订审批队列 + 证件催补清单 + 投诉登记（P1） |

## 4. 两侧状态映射表（核心）

> 唯一事实源在后端；游客侧为「只读投影」，由后端状态实时推导。

| 游客侧状态（C 端展示） | tour.plan.reg（报名） | tour.plan（团） | tour.payment.claim（收款） | 游客可见动作 |
|------------------------|----------------------|-----------------|----------------------------|-------------|
| **待确认** | 已生成，未确认 | draft | 待收款/待认领 | 补录证件、线下付款 |
| **待成团** | 已确认 | pending（未达 min_seats） | 部分/未收款 | 等待成团（显示人数缺口） |
| **已成团/待出行** | 已确认 | confirmed / operating | 已审核/部分 | 查进度、退改签（按规则） |
| **出行中** | — | in_progress | — | 行程/集合信息 |
| **已完成** | — | completed | 已平账 | 评价（P2）、电子行程单 |
| **已取消（游客退订）** | cancelled | cancelled | 退款中/已退 | 退款进度 |
| **未成团已取消** | cancelled | cancelled | 已退/无需收 | 退款进度 |
| **已改签** | 已改签（指向新班期） | （新团） | 补差/退差 | 新班期信息 |

**推导规则**（dev 落地时写成 computed / 视图映射）：

- 「待成团」= `plan.state == 'pending'` 且 `plan.guest_count < departure.min_seats`
- 「已成团」= `plan.state in (confirmed, operating)`
- 「已取消」= `plan.state in (cancelled, refunded)` 或 `reg` 关联退订申请 approved
- 「待确认」= `plan.state == 'draft'`

## 5. 关键业务规则

### 5.1 成团阈值与成团失败处理（G4，新增，已拍板 D2）

- 字段：`tour.departure.min_seats`（成团最低人数，默认 0 = 不启用）
- 判定：报名累计 `guest_count ≥ min_seats` 才允许 `action_confirm` 成团
- 成团截止：`tour.departure.deadline_date`（默认出发前 **3 天**，短途 1-2 天团可设 1 天，班期级可覆盖）
- **未成团处理**：
  - **默认动作 = 自动全额退款（P0）**：到期仍未达阈值 → 该班期团自动 `cancelled` + 已收报名单**全额退款（原路退回）** + 释放余位 + 短信/邮件通知游客。未成团属旅行社责任，**不收取违约金**。
  - **可选动作 = 转散客（P1）**：退款通知中附带「可转班期」选项（同线路其他已成团班期，复用改签机制）；游客在截止前选择转团则改签、不退，未选择则按默认执行全额退款。
- 兜底：`min_seats=0` 时行为与现状一致（计调手动确认），不破坏存量团

### 5.2 退订规则（已拍板 D6：默认全退，梯度可选）

- **默认全额退款（100%）**：梯度扣费为可选配置、默认**不启用**；启用后按「班期级 > 线路默认 > 全局兜底」三层配置（§5.7）
- 可选梯度模板（启用时参考默认值，可调）：距出发 `>30 天` 退 100%、`15-30 天` 退 80%、`7-15 天` 退 50%、`3-7 天` 退 20%、`<3 天` 退 0%
- 退款金额 = 已收款 × 比例；差额为违约金收入
- 退款动作：独立退款单或负数红冲（对齐 BS-02 §6.4），必须关联原收款/原团并审批；在线支付退订走**原路退回**
- 释放余位：审批通过即 `booked_seats -= N`

### 5.3 改签规则

- 仅限同一线路不同班期（跨线路 = 退订 + 重新报名）
- 改签重计价（新班期五档价快照），差价多退少补
- 已出行/已归档团禁止改签
- 改签生成 `tour.plan.change` 留痕（复用溯源）

### 5.4 证件补录时限

- 截止 = 出团前 7 天（`tour_website.id_deadline_days` 可配）
- 出团前 3 天未补全 → 预警 + 短信；截止未补全 → `id_incomplete=True`，出团前置校验可拦截

### 5.5 支付方式（已拍板 D1）

| 方式 | 优先级 | 说明 |
|------|:------:|------|
| 微信支付在线收银台 | **P0** | 本期唯一在线渠道；接 payment provider（wechat），落账仍归 claim，退款原路退回 |
| 线下转账/到店/现金 | **P0** | 现状保留 + 在线支付失败/超时兜底，走 payment.claim 认领 |
| 支付宝在线收银台 | **P1** | 复用微信接入层，仅 provider 不同 |
| 银联/银行卡 | **P2** | 散客自助报名占比极低，本期不做 |
| 签单/挂账 | P2 | 团款月结（现有 pay_way.is_credit 已支持） |

### 5.6 满团 / 超卖处理

- 提交时事务内校验 `total_people > remain_seats` 报「余位不足」
- `tour.departure` 有 `_check_seats_not_oversold` 兜底（booked_seats ≤ seats）
- 并发下单：建议 P1 加**乐观锁/行级锁**（当前依赖 Python 事务 + 兜底 constraint，极端并发下有余位校验竞态）
- 满团后班期在 C 端置灰「已满」

### 5.7 配置粒度（已拍板 D3）

成团 / 退订 / 证件截止等规则统一采用**三层配置，逐级回退**：

| 层级 | 位置 | 优先级 | 说明 |
|------|------|:------:|------|
| 班期级 | `tour.departure`（min_seats / deadline_date / 退订梯度） | 最高 | 临期促销、冷门班期差异化 |
| 线路默认 | `tour.line`（线路级默认值） | 中 | 同类产品统一规则 |
| 全局兜底 | 系统配置（ir.config_parameter） | 最低 | 无配置时行为一致（min_seats=0、退订全退、证件截止 7 天） |

读取顺序：班期 → 线路 → 全局；上层未设值则回退到下一层。**确认为唯一配置口径，不另设配置模型。**

## 6. 模块边界与依赖

| 模块 | 职责（本设计后） | 依赖 | 禁止 |
|------|------------------|------|------|
| **tour_website** | C 端展示 + 无登录报名 + **订单中心（查询/证件补录/退订改签申请）** + 游客侧状态投影 + 成团阈值字段 | tour_product、tour_order、portal | 不依赖 sale；不直接写财务分录 |
| **tour_website_sale** | 电商下单桥接（sale.order.line → 共享方法）+ 在线支付收银台入口 | website_sale、tour_website | 不独立出账；不重复实现校验/计价 |
| **tour_order** | 团/报名/状态机、并团、变更、退订审批承接 | tour_product | 不依赖 website；退订申请模型放这里或 tour_website 均可（建议放 tour_order，与 plan.change 同层） |
| **tour_operation** | 计调运营（project.task booking）、冲突检测、出团前置校验 | tour_order、tour_resource | — |
| **tour_accounting** | 收款认领、单团核算、佣金、退款分录 | tour_order | 财务唯一口径；退订退款分录在这里 |

**关键边界约定**：

1. 「校验 + 计价 + 建团 + 回写余位 + 汇总」唯一入口 = `tour.plan.reg._create_plan_reg_from_order`（tour_website），电商/轻量报名/未来任何渠道共用。
2. 「退订释放余位 + 退款」唯一入口 = 退订审批通过动作，`booked_seats` 只允许经由报名（+）和退订/取消（−）两个原子方法变更，禁止裸写。
3. `sale.order` 全程不产生 `account.move`（收入确认仍由 tour.plan 的 analytic 核算产出）。

## 8. 与现有实现的差异点（保留 / 改造 / 新增）

### 8.1 保留（不动）

- 共享服务方法 `_create_plan_reg_from_order` 一套逻辑（校验/计价/建团/回写/汇总）
- 财务唯一口径 tour.plan，sale.order 不独立出账
- `tour.departure` 五档价 `get_online_prices`（班期价→线路价回退）
- `from_type` 6（线上官网）/ 7（电商）渠道标识
- 客人证件子表 `tour.plan.reg.passenger`（加密）
- 收款认领复用 `tour.payment.claim`（不另建收款流程）
- 后端 10 态状态机、并团 `first_plan_id`、单团变更溯源

### 8.2 改造（增强，不推翻）

| 现有 | 改动 | 理由 |
|------|------|------|
| `_get_or_create_plan` 建 draft 团 + 计调手动确认 | 增加 `min_seats` 阈值判定 + 未成团超时取消 | 成团从"人工开关"变"规则驱动" |
| `booked_seats += N` 单向递增 | 增加退订/取消的 `booked_seats -= N` 原子释放 | 余位只增不减是超卖隐患 |
| 报名成功页静态回执 | 升级为订单中心入口（状态徽标 + 后续动作） | 游客下单后无处可去 |
| `tour.departure`（五档价） | 增加 `min_seats` / `deadline_date` / 退订梯度配置 | 承载成团与退订规则 |

### 8.3 新增（缺口）

- 游客订单中心路由（查询）
- 退订申请模型 `tour.plan.reg.cancel` + 审批
- 改签申请动作（复用 change 溯源）

## 9. 异常处理矩阵

| 异常 | C 端表现 | 后端动作 | 数据一致性 |
|------|---------|---------|-----------|
| 满团（余位不足） | 班期置灰「已满」，提交报「余位不足」 | 拦截 + 兜底 constraint | 余位不超卖 |
| 并发抢最后一位 | 一方成功、一方「余位不足」 | P1 乐观锁兜底 | booked_seats 准确 |
| 未成团超时 | 「未成团已取消」+ 退款进度 | 自动取消 + 全额退款 + 释放余位 | 金额/余位同步 |
| 退订申请 | 提交后显示「退款中」 | 审批→释放余位→退款分录 | 余位释放 + sum_money_return |
| 改签换班期 | 显示新班期信息 | 原班期释放 + 新班期占位 + 重计价 + change 记录 | 两班期余位都正确 |
| 证件未补全 | 出团前提醒「补录证件」 | 预警 + 出团前置可拦截 | passenger 子表完整 |
| 支付失败/超时 | 回执仍有效，提示线下付款 | 不生成 claim，订单不确认 | 金额不变 |
| 重复提交（幂等） | 提示「请勿重复提交」 | reg_code 唯一约束 + 前端防重 | 不重复扣余位 |
