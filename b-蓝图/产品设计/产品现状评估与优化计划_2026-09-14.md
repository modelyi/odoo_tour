## 3. 后续优化计划（分阶段）

> 排序原则不变：**先补 P0 硬缺口让主线完整 → 再补 P1 报表与完整性 → 最后 P2 体验**。每项给价值 / 成本 / 优先级。

### 阶段一（近期，P0 补缺）—— 目标：主线无硬缺口，可对外宣称「无缝迁移」

| # | 功能 | 价值 | 成本 | 优先级 | 交付物 |
|---|------|------|------|:------:|--------|
| 1 | 购物退单/补单/成本录入（F-03） | 购物返佣是易途 §5 佣金核心，缺退/补/成本则购物财务失真 | 中（扩展 tour.shop.record 4 字段 + 状态机 + 批量收款向导） | **P0** | record_type / cost_amount / settle_state / payment_id + 批量收款向导 |
| 2 | 司陪导协议 / 导游人均线 / 人均算法（F-04） | 返佣自动计算的前提，直接决定购物佣金钱数对错 | 中高（3 个协议子模型 + 人均算法规则） | **P0** | 司陪导协议 + 人均线设置 + 返佣自动计算闭环 |
| 3 | 二次结算（F-05） | 与供应商额外结算，易途 §6 关键特点，营运中心高频 | 中（tour.order.return 薄层 + 分级审批 + 分录） | **P0** | 追加/退款二次结算 + 审核 + 查询 |

## 4. 风险与建议（产品层面）

### 4.1 数据缺口（🔴 最高优先级待决策）

- **购物记录、计调预订两块"无源可迁"是当前最大业务风险**：模型在、逻辑在，但历史数据为 0。若直接上线，购物返佣统计、计调排班报表对历史团是空的。
- **建议（需 PM/管理层拍板）**：
  1. 短期接受「空表上线 + 新团手工录入」，历史购物/预订数据不补（旧团已归档，补历史 ROI 低）；
  2. 或安排一次「回到易途抓明细接口」的专项，补齐 PlanShop* / PlanOrderAssign* 表 —— 需评估海螺是否还在用易途、接口是否可达。
  - **本 PM 倾向方案 1**：主线已跑通，历史数据补录价值有限，把资源投入 P0 功能而非追历史数据。

### 4.2 无源/半实现功能

- **CRM 销售跟单、计调 project.task**：能力已装但 0 数据、未走单，属「有源无流」。若不尽快走一遍真实业务单，UAT 覆盖是纸面的。建议阶段一验收时强制「真实业务走单」而非纯 shell 断言。
- **购物协议偏薄**：当前协议只支撑固定返佣比例，司陪导协议/人均线缺位会直接导致返佣自动计算做不出来，这是 P0 的「根」，优先于购物报表。

### 4.3 遗留缺陷（P1 差额征税申报口径）

- 09-13 UAT 发现 `_plan_cost_vat_split` 用 `abs()` 导致抵减凭证贷方行被重复计入可扣除成本，`vat_deduct_amount` 3600→3803.77 失真，影响增值税申报附列资料三。**这是影响申报合规的 P1，建议在阶段一或更早修复**，优先级不亚于购物补缺。

### 4.4 范围蔓延风险

- 旧路线图（2026-09-12）规划 Phase 3 的票务/车队/同业分销/移动端，与「易途对标缺口清单」的「不做」边界矛盾。**建议 PM 统一口径**：票务/B2B/移动端在核心主线验收 + 海螺 Pilot 前冻结，避免蓝图多头打架。

### 4.5 度量口径风险

- 供应商「10 类 vs 12 类」、导游「2170 vs 2173」等计数在历次 UAT 间有 ±2~3 漂移（验收期间新增/归档所致），非缺陷，但建议在文档中统一口径为「active_test=False 全量」或「active 口径」并标注，避免汇报时对不上数。
