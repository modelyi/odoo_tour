## 1. 业务背景

### 1.1 定位

海螺旅行社目前以「易途系统」内部录单为主，客人通过门市/销售电话/微信报名，由销售或计调手工录入订单。本规格在既有 TMS 模型之上，打通一条**最小 C 端闭环**：

```
官网展示线路 → 在线报名（线下付款） → 报名落库 → 内部计调/财务复用既有流程
```

**不做**（明确排除，避免与后续模块重复）：

| 排除项 | 原因 |
|--------|------|
| 在线支付 | 本规格为「线下付款」最小闭环，在线支付（微信/支付宝收银台）属后续 PRD-07 小程序商城 |
| B2B 同业分销/门户 | 已有 tour_b2b 规划（P2），本规格不含 |
| 会员体系/登录中心 | 最小闭环支持「无登录报名 + 手机号验证」，不做完整会员/积分 |
| 在线签约/电子合同 | 报名回执先行，电子合同属 P2 |

### 1.2 最小闭环

1. **线路展示**：官网展示 `tour.line`（线路），含线路详情、行程（`tour.line.detail`）、价格、发团日期（`tour.departure`）、余位
2. **在线报名**：客户选线路 + 选发团日期 → 填报名信息（联系人/人数/证件/联系方式）→ 提交生成报名单（`tour.plan.reg`）
3. **落库到既有模型**：报名关联发团计划（`tour.plan`），不新造订单体系
4. **线下付款**：下单后不支付，客户按回执指引线下转账/到店付款，财务走既有收款认领（`tour.payment.claim`）
5. **客户体验**：无登录可报名（可选手机号验证码），报名成功即时回执

### 1.3 依赖的既有模块（已实现，直接复用）

| 模型 | 位置 | 本规格中的角色 |
|------|------|----------------|
| `tour.line` | tour_product | 线路产品（名称/天数/价格/行程/费用说明） |
| `tour.line.detail` | tour_product | 按天行程明细（第 N 天/标题/城市/餐饮/住宿/交通/内容） |
| `tour.departure` | tour_product | 发团计划（出发日期/返程日期/总位数/已订位/余位/门市价/发布状态） |
| `tour.plan` | tour_order | 团队订单/发团计划（团号/状态机/金额/会计） |
| `tour.plan.reg` | tour_order | 报名单（联系人/人数/金额/并团指针） |
| `tour.payment.claim` | tour_accounting | 收款登记/认领（线下付款落账、核销应收） |
| `res.partner` | Odoo 标准 | 客户档案 |

## 3. 业务流程

### 3.1 线路展示与报名（C 端主流程）

```
客户打开官网
    ↓
线路列表（分类/目的地/关键字筛选，展示 名称/天数/起价/发团日期数）
    ↓
线路详情页（行程 tour.line.detail、费用包含/不含、温馨提示、
             可选发团日期 tour.departure + 余位 remain_seats + 价格）
    ↓
选择发团日期（仅 state=published 且 remain_seats > 0 可选）
    ↓
填写报名信息（联系人姓名/手机/各类型人数/客人证件/备注）
    ↓
[可选] 手机号验证码核验
    ↓
提交 → 系统校验余位与人数 → 生成报名单 tour.plan.reg
    ↓
报名回执（报名单号 + 应付金额 + 付款指引 + 客服联系方式）
    ↓
客户线下付款（转账/到店）
```

### 3.2 线下付款与收款认领（复用 BS-06）

```
客户按回执线下打款
    ↓
出纳收款登记 tour.payment.claim（pay_channel=银行转账/现金，pay_money=到账金额）
    ↓
业务员/销售收款认领 → 关联 tour.plan（线上报名的团队订单）
    ↓
会计审核 → 生成收款凭证、核销应收
    ↓
报名单 sum_pay_normal 回写、tour.plan sum_pay / sum_un_pay 更新
```

> 与 BS-06 完全一致，无需为线上订单另建收款流程。差异仅在于：线上报名单的 `from_type`/渠道标记为「官网」，便于财务认领时按渠道定位。

### 3.3 报名后内部流转（复用 BS-02）

```
tour.plan.reg（待确认） → 销售确认（confirmed）
    → 计调操作 → 出行 → 完成 → 归档
```

线上报名的报名单进入既有 `tour.plan` 状态机与并团逻辑，无需特殊处理。

### 4.2 线路详情页

| 功能 | 说明 | 业务规则 |
|------|------|----------|

| 发团日期与余位 | 该线路所有 `state=published` 且未过期的 tour.departure，展示出发日期、天数、余位 remain_seats、成人价/儿童价 | 余位 ≤ 0 显示「已满」不可选 |
| 价格口径 | 展示发团计划门市价（tour.departure.price_adult/price_child）；老人/学生/婴儿价回退 tour.line 对应价格 | 见 §6 计价规则 |

### 4.3 在线报名表单

| 字段 | 必填 | 说明 |
|------|:----:|------|
| 线路 + 发团日期 | ✓ | 由详情页带入，不可改（回跳可重选） |

| 联系人手机 | ✓ | 落 supplier_user_mobile，11 位校验 |
| 联系人座机 | ✗ | 落 supplier_user_tel |
| 客户/单位名称 | ✗ | 落 supplier_name，默认=联系人姓名 |
| 成人数 / 儿童数 / 老人数 / 学生数 / 婴儿数 | 至少 1 类 ≥ 1 | 落 adult_num/child_num/old_man_num/student_num/baby_num |
| 客人证件（每人） | ⚠️ 见 §5.2 | 姓名 + 证件类型 + 证件号（按人数逐条填写） |
| 职业 / 民族 / 省份 / 城市 | ✗ | 落 guest_occupation/nation/province/city_name |
| 备注 | ✗ | 落 remark |
| 手机验证码 | 可选 | 无登录报名时可选核验，P2 依赖短信网关 |

### 4.4 报名回执

提交成功后展示（并可短信/邮件推送，P2）：

- 报名单号（reg_code）
- 线路 + 发团日期 + 人数
- 应付金额（in_com_quo_sum）
- 付款方式指引（收款账户/到店地址/客服电话）
- 提示「报名不代表出行，以销售确认为准」

### 4.5 后台承接

| 功能 | 说明 |
|------|------|
| 线上报名查询 | tour.plan.reg 列表按 from_type=线上官网 过滤 |
| 渠道标记 | 报名单/团队订单标记官网来源，用于业绩归属与统计 |
| 余位回写 | 报名成功后 tour.departure.booked_seats 递增，remain_seats 递减 |

### 5.2 关键设计决策与缺口（product-architect 需裁定）

> 以下 4 项是线上销售落地前必须补齐/裁定的模型缺口，均已标注建议方案。

**GAP-1：`tour.departure`（发团计划）与 `tour.plan`（团队订单）无显式关联**

- 现状：C 端展示用 `tour.departure`（轻量：日期/余位/门市价/发布态），而报名单 `tour.plan.reg.plan_id` 指向的是 `tour.plan`（重团队订单：团号/状态机/会计）。两者当前**没有任何外键**。
- 建议方案（推荐 A）：
  - 给 `tour.plan` 增加 `departure_id = M2O('tour.departure')`（可空，仅线上发布计划回填）。
  - 线上报名时：按 `departure_id` 查找该发团计划是否已生成团队订单；无则**自动创建**一个 `tour.plan`（biz_mode='12'、plan_type='2'、from_type=线上、line_id=departure.line_id、begin_date/end_date=departure.start_date/end_date、回填 departure_id），团号按「线路+出发日期」规则生成。
  - 报名单 `plan_id` 指向该 `tour.plan`，`first_plan_id` 同指向（团期计划语义，见 BS-02 §4.2）。
- 备选方案 B：`tour.departure` 发布时由后台手动/批量生成对应 `tour.plan`，线上报名只做查找匹配。
- 无论 A/B，都必须保证：**一个已发布发团计划对应一个团队订单**，线上报名直接落到该团，余位从 `tour.departure` 实时回写。

**GAP-2：报名单无「客人证件」字段**

- 现状：`tour.plan.reg` 只有联系人（supplier_user + 手机/座机）和人数（adult_num/child_num/…），**没有每位客人的证件号码字段**。而实名制/保险/机票火车票实名均需要证件。
- 建议：新增客人明细子表 `tour.plan.reg.passenger`（参考第三方参考 `tour.passenger` 模型，精简为最小字段）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|:----:|------|
| reg_id | M2O→tour.plan.reg | ✓ | 所属报名单 |
| name | Char | ✓ | 客人姓名 |
| passenger_type | Selection | ✓ | adult/child/old_man/student/baby |
| id_type | Selection | ✓ | id_card（身份证）/passport（护照）/other |
| id_number | Char | ✓ | 证件号 🔴 加密存储 |
| price | Float | | 该客人单价（计价用） |
| sequence | Integer | | 排序 |

- 若最小闭环暂不做逐人证件，则至少在 `tour.plan.reg` 增加 `id_number`（联系人证件号，单证件简化），并在验收中明确「多人报名暂不支持逐人证件」。**本规格默认采用逐人子表**（保险/实名是硬需求）。

**GAP-3：无「线上官网」渠道/来源标识**

- 现状：`from_type` 仅 ('1' 内部 / '5' 同行 / '4' 异常)，无线上渠道值。
- 建议：`tour.plan` 与 `tour.plan.reg` 的 `from_type` 增加 `('6', '线上官网')`；同时在 `tour.plan.channel_name` 写入「官网线上」，用于业绩/渠道统计与财务认领定位。

**GAP-4：发团计划价格仅成人/儿童两档**

- 现状：`tour.departure` 仅 `price_adult`/`price_child`，而报名人数类型有 5 类（成人/儿童/老人/学生/婴儿）。
- 建议：最小闭环价格优先取 `tour.departure.price_adult/price_child`，老人/学生/婴儿价回退 `tour.line.old_man_price/student_price/baby_price`；或给 `tour.departure` 补齐老人/学生/婴儿价字段（推荐，避免价格口径二义）。

### 5.3 计价规则（线上报名自动计价）

```
in_com_quo_sum = adult_num×成人价 + child_num×儿童价 + old_man_num×老人价
               + student_num×学生价 + baby_num×婴儿价
```
- 单价优先级：发团计划价（tour.departure）→ 线路模板价（tour.line）
- 报名单 `sum_un_pay` 初始 = in_com_quo_sum（全部未收）
- 报价金额为「快照」：下单时锁定，后续调价不影响已生成报名单（对齐 BS-02 §6.1 预报价语义）

### 5.4 关联关系（新增后）

```
tour.line (1) ──→ (N) tour.departure            （发团计划，含余位/门市价）
tour.line (1) ──→ (N) tour.plan                 （团队订单）
tour.departure (1) ──→ (1) tour.plan            （GAP-1 新增 departure_id 回链）
tour.plan (1) ──→ (N) tour.plan.reg             （报名）
tour.plan.reg (1) ──→ (N) tour.plan.reg.passenger  （GAP-2 新增客人明细）
tour.plan (1) ←── (N) tour.payment.claim        （线下付款认领，复用 BS-06）
```

## 6. 业务规则

1. **可见性**：仅 `active=True` 且 `audit_state=approved` 的线路；仅 `state=published` 且 `remain_seats>0` 且 `start_date≥今天` 的发团计划可在线报名
2. **余位校验**：报名人数 ≤ 余位 remain_seats；提交后 booked_seats 递增、remain_seats 重算（并发下单需加锁/乐观锁防超卖）
3. **人数校验**：至少 1 类人数 ≥ 1；guest_count = Σ各类型 − baby_num；与 BS-02 §7.7 规则一致
4. **手机号校验**：11 位手机号格式；可选验证码核验（P2）
5. **证件校验**：证件号非空且格式校验（身份证 18 位/护照规则）；证件 🔴 加密存储、界面脱敏
6. **价格校验**：各类型单价 ≥ 0；儿童价 ≤ 成人价（对齐 BS-01 §4.4）
7. **渠道标记**：线上报名 from_type='6'、channel_name='官网线上'，不可被销售手工改写为内部来源（业绩防作弊）
8. **状态流转**：报名单初始对应 tour.plan 的 draft/pending，进入 BS-02 状态机；已取消/退款报名释放余位
9. **线下付款**：线上报名不触发支付，sum_pay_normal 初始为 0；付款经 tour.payment.claim 认领后回写（复用 BS-06 状态机 0→1→2→3）
10. **回执**：提交成功即回执；报名单号 reg_code 唯一，作为客户线下付款/客服沟通凭证

| 字段 | 安全等级 | 说明 |
|------|---------|------|
| 客人证件号 id_number | 🔴 加密存储 | 实名/保险必需，界面脱敏（仅财务/计调按权限可见） |
| 联系人手机 supplier_user_mobile | 🟡 脱敏展示 | 列表掩码，详情按权限 |
| 客人职业 guest_occupation | 🟡 按权限脱敏 | 对齐 BS-02 §9 |
| 报名回执（C 端） | 仅显示本单信息 | 不得泄露他人报名/证件数据，接口需鉴权 |

**三条硬性红线（对齐 BS-02 §9）**：

1. 证件号禁止明文入库/明文回显，加密存储 + 字段级权限
2. 线上报名接口（无登录）必须防刷：验证码/频率限制/一次性令牌
3. 回执与查询接口严格隔离：客户仅能凭「报名单号 + 手机号」查询本人报名，不得遍历他人数据

## 9. 与易途系统对标

| 易途功能 | 本系统实现 |
|----------|-----------|
| （易途为内部录单，无 C 端官网卖线路） | 本规格为新增能力：官网线路展示 + 在线报名 |

- 打通 C 端自主报名，减少销售手工录单，降低录入成本
- 渠道来源结构化标记（from_type/channel_name），可做线上获客归因
- 报名即时回执 + 余位实时，提升客户体验、防超卖
