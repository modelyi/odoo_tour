## 一、遗漏的需求点清单

### 1.1 收款主字段映射错误（影响 BS-05/06/07）

**数据事实**（team_orders.csv，86,925 条）：

| 字段 | 非零条数 | 合计金额 | 说明 |
|------|:-------:|--------:|------|
| outPrice_QuoSum（报价总额） | 660 | 126 万 | **仅 BizMode=14 有值**，非通用应收字段 |
| SumPay_Normal（正常收款） | 75,073 | 1.77 亿 | **真正的"已收款"主字段** |
| SumPay（已收款合计） | 75,282 | 2.36 亿 | = SumPay_Normal + SumPay_Delegate |
| SumMoney_Delegate（代收金额） | 13,899 | 6,044 万 | 代收代付规模可观 |
| SumPay_Delegate（代收已付） | 13,506 | 5,922 万 | |
| SumUnPay（未收款） | 4,937 | 1,463 万 | |
| InCom_QuoSum（成本总额） | 79,731 | 2.52 亿 | |

**问题**：BS-05 §2.1.2/§2.3.1 及 BS-06 将 `outPrice_QuoSum` 当作收入确认金额来源，但数据中 86,265/86,925（99.2%）的团队该字段为 0。收入确认不能依赖它。

**遗漏需求点 F-01**：必须建立**收款金额多字段映射规则**：
- `SumPay_Normal`（正常收款）→ 应收账款核销主字段
- `SumMoney_Delegate` / `SumPay_Delegate`（代收/代收已付）→ 代收代付核算（对应 BS-06 第六节，但字段名需对齐）
- `SumUnPay`（未收款）→ 应收账款余额（含账龄分析）
- `outPrice_QuoSum`（报价总额）→ 仅作**组团社报价单应收**（BizMode=14），不作通用收入确认依据

### 1.2 退款字段完全遗漏（影响 BS-05/06）

**数据事实**：
- `SumMoney_Return`（退团款金额）：10 条非零，合计 2.08 万
- `SumPay_Return`（退团款已付）：3 条非零，合计 1.92 万
- **负数金额普遍**：11,193 条 SumPay_Normal < 0，1,014 条 SumPay < 0，501 条 SumUnPay < 0（负数即退款/冲抵/红冲）

**问题**：BS-06 收款流程 R-01 假设 `PayMoney > 0`，但团队级金额大量为负（退款冲抵）。BS 文档无「团款退款」流程。

**遗漏需求点 F-02**：新增**团款退款流程**（客户退款）：
- 退款场景：客人退团、取消订单、超收退还
- 字段映射：SumMoney_Return（应退）→ 2241 其他应付款—客户退款；SumPay_Return（已退）→ 银行存款核销
- 负数金额处理：收款登记需支持**红字/负数冲抵**，或独立退款单，禁止简单"金额>0"校验一刀切
- 合规：退款需关联原收款、原团队，审批后执行（[内控-授权审批]）

### 1.3 开票金额字段遗漏（影响 BS-05/07 差额征税）

**数据事实**：
- `InvoiceMoney`（已开票）：全部为 0
- `UnInvoiceMoney`（未开票）：79,731 条，2.52 亿 —— **与 InCom_QuoSum 完全相等**

**问题**：所有成本在演示数据中均未开票。这是差额征税（财税[2016]36号）的最大合规风险点。BS-05/07 提到了"发票归集"概念，但未映射 `InvoiceMoney`/`UnInvoiceMoney` 字段。

**遗漏需求点 F-03**：新增**发票管理需求**：
- 字段映射：InvoiceMoney（已开票金额）→ 已取得合规发票金额；UnInvoiceMoney（未开票金额）→ 发票缺口
- 按团队/供应商/成本类型维度统计发票归集率
- 差额征税申报时，`UnInvoiceMoney > 0` 的成本不得作为可扣除项目申报
- 发票缺口预警：`未开票金额 / 已付金额` 超阈值自动预警

### 1.4 请款/付款申请字段遗漏（影响 BS-06）

**数据事实**：
- `ApplyPayMoney`（申请付款金额）：75,073 条 = SumPay_Normal（完全相同）
- `UnPay_Apply`（未付申请）：4,937 条 = SumUnPay（完全相同）
- `ApplyPay_UnChk`（未审核申请付款）：全 0

**问题**：BS-06 第四节请款流程未映射这三个易途字段，且 `UnPay_Apply == SumUnPay` 暗示"未收款"与"未付申请"在源系统是同一口径，需厘清。

**遗漏需求点 F-04**：请款单需映射易途字段：
- `ApplyPayMoney` → 请款已申请金额
- `UnPay_Apply` → 未付申请金额（= 应付余额）
- `ApplyPay_UnChk` → 待审批请款金额
- 厘清 UnPay_Apply 与 SumUnPay 的语义差异，避免重复计入

### 1.5 代收代付规模确认（影响 BS-06 第六节）

**数据事实**：SumMoney_Delegate（代收金额）13,899 条、6,044 万，占总收款（SumPay 2.36 亿）约 26%。代收代付并非边缘业务。

**遗漏需求点 F-05**：BS-06 §6 代收款核销需升级为**一等公民流程**：
- 代收金额占收款总量 ~26%，需独立科目（2241.01 其他应付款—代收团款）与自营收入严格分离
- 代收余额核销（SumPay_Delegate vs SumMoney_Delegate 差额 = 未核销代收款）需账龄跟踪
- 代收涉及的第三方（签证/保险/门票代订）需单独对账

### 1.6 结算方式定义错误（影响 BS-05 §3.1）

**数据事实**（pay_ways.csv 7 条）：

| PayWayID | PayWay | PayWayName | PayWayType | 含义 |
|:-------:|:------:|-----------|:----------:|------|
| 1 | -2 | 签单 | 0 | 签单（月结信用） |
| 2 | 1 | 导游现付 | 2 | 导游现场支付 |
| 3 | 3 | 导游现收 | 1 | 导游现场收款 |
| 5 | 0 | 公司现付 | 2 | 公司直接支付 |
| 6 | 0 | 公司现收 | 1 | 公司直接收款 |
| 7 | 111 | 企业码支付 | 2 | 企业二维码付款 |
| 8 | -111 | 企业码员工代付 | 2 | 员工扫码代付 |

**问题**：BS-05 §3.1 假设 7 种结算方式为「现金/银行转账/微信/支付宝/POS/支票/其他」——**完全错误**。真实 7 种是**收付场景**（公司/导游/签单/企业码），PayWayType 是 0=签单 / 1=收款 / 2=付款。

而 pay_claims.csv 的 `PayType` 字段实际存的是**支付渠道**：银行转账(42)/微信(5)/现金(2)/支付宝(1)/其他(1)。

**遗漏需求点 F-06**：**两个维度必须拆开建模**：
- **收付场景**（pay_ways：公司现收/公司现付/导游现收/导游现付/签单/企业码支付/企业码员工代付）→ 决定会计分录方向与科目（现金/银行/其他货币资金/应付）
- **支付渠道**（PayType：银行转账/微信/支付宝/现金/其他）→ 决定资金账户（对应 accounts 中的微信/支付宝/现金账户）
- 签单（PayWayType=0）必须特殊处理：不产生即时收付，转签单单据月结流程（BS-07 §3.3）

### 2.2 银行卡号（BankAccountNo）合规存储要求

`[内控-数据安全]` 银行卡号属《个人信息保护法》第 28 条**敏感个人信息**及《数据安全法》重要数据，必须：

1. **加密存储**：数据库落盘必须加密（AES-256-GCM 或国密 SM4），不得明文存储。Odoo 侧 `res.partner.bank.acc_number` 字段需加字段级加密扩展，或存密文+密钥管理服务（KMS）分离。
2. **展示脱敏**：界面默认只显示掩码 `****后4位`（如 `****4051`），完整卡号需"查看"授权 + 二次鉴权 + 操作留痕。
3. **最小化访问**：按角色授权——只有出纳、财务经理、付款执行场景可申请查看完整卡号；业务员、导游、计调一律只见掩码。
4. **日志脱敏**：审计日志、导出文件、报表中一律不出现完整卡号；日志记录卡号字段时自动替换为掩码。
5. **导出管控**：含卡号的导出需审批，导出文件加密，且默认脱敏。
6. **密钥管理**：加密密钥与密文分离存储，密钥轮换有流程，密钥泄露有应急预案。
7. **与 Odoo 映射**：`res.partner.bank.acc_number` 保持掩码展示，完整值走加密扩展字段；`account.payment` 生成付款指令时仅在内存中解密拼装。

### 2.3 身份证号（IDNum）合规存储要求

`[内控-数据安全]` 导游/司陪/客户身份证号（BS-06 §5.3 guide_id_num、BS-08 id_number）：

1. 加密存储，展示掩码 `前3位 + **** + 后4位`。
2. 个税代扣代缴申报（[个税法]）需要完整身份证号 → 申报导出时解密，导出即加密包，限定财务申报岗使用。
3. 与银行卡号同等级别的访问审计。
