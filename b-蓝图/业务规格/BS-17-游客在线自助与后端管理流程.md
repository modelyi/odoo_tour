## 1. 业务背景与定位

### 1.1 定位

本规格从**旅行社业务视角**重新梳理「游客在线自助 + 后端管理」的全链路，补齐 BS-13（线上销售）与 TDS-PROD-001（电商桥接）已实现的**技术闭环**之上缺失的**业务规则层**：成团阈值、证件时限、退订违约金、改签、包团、状态对齐。

**已实现（代码实测，2026-09-14）**：

| 能力 | 实现 | 位置 |
|------|------|------|
| 线路 product 化 | `tour.line` 委托继承 `_inherits={'product.template': 'product_tmpl_id'}` | tour_product |
| 班期（余位/价格/发布态） | `tour.departure`（seats/booked_seats/remain_seats/五档价/draft-published-ended） | tour_product / tour_website |
| 团队订单（财务唯一口径） | `tour.plan`（10 态状态机 + 金额 + analytic） | tour_order / tour_accounting |
| 报名（并团指针） | `tour.plan.reg`（plan_id 挂团 + first_plan_id 并团指针） | tour_order |
| 无登录轻量报名 | `create_online_reg` → 共享方法，`from_type='6'` 线上官网 | tour_website |
| 电商下单 | `sale.order` 确认 → `_bridge_to_plan_reg` → 共享方法，`from_type='7'` 电商 | tour_website_sale |
| 共享服务方法 | `_create_plan_reg_from_order`（校验余位→建/定位团→建报名→回写余位→汇总团金额） | tour_website |
| CRM 转团 | `crm.lead.action_convert_to_plan`（won→draft，回写 lead_id） | tour_order |
| 客人证件逐人子表 | `tour.plan.reg.passenger`（加密落盘） | tour_website |

### 1.2 当前业务缺口（本规格要补的规则层）

1. **游客侧无订单状态**：`tour.plan.reg` 无独立 state 字段，游客在 C 端看不到「待支付/已支付/已成团/待出发/已出行/已退订」等订单状态，只能凭报名单号。
2. **无成团阈值**：`tour.departure` 无 `min_seats`/成团截止，何时「确认成团」无规则，完全靠计调经验判断。
3. **无证件时限规则**：有证件子表，但「哪些团必须提前收证件、提前多久」无规则。
4. **无退订违约金规则**：`tour.plan.reg` 无取消动作，且**取消/退订不释放余位**（`booked_seats` 只增不减）。
5. **无改签规则**：改班期/改人数/跨线路改签无业务定义（仅 BS-02 的单团变更 `tour.plan.change` 设计）。
6. **包团/代订/自由行**：业务模式存在（BizMode=1/41/51），但 C 端+后端的自助流程未定义。

## 4. 业务流程（分场景）

### 4.1 散客在线报名 → 成团 → 出行（主线）

```
【游客侧】                        【系统/后端】
浏览线路/详情/班期（published 且 remain_seats>0 且 start_date≥今天）
    ↓
选班期 + 填五档人数 + 联系人 + 逐人证件
    ↓
提交下单（无登录 6 / 电商购物车 7）
    ↓                            → 共享方法 _create_plan_reg_from_order：
    │                                校验余位/人数/手机/证件
    │                                → _get_or_create_plan（同 departure 复用团，首个下单建 draft 团）
    │                                → 建 reg（reg_code / plan_id / first_plan_id）
    │                                → 回写余位 booked_seats += 人数
    │                                → 汇总团金额 _sync_amounts_from_regs（幂等 Σregs）
订单状态：待支付                     reg 落库 sum_pay_normal=0
    ↓
付款（在线支付 P3 / 线下转账）       → 收款认领 tour.payment.claim（BS-06）
订单状态：已支付/待确认              reg.sum_pay_normal 回写，plan.sum_pay 更新
    ↓
                                   → 计调确认成团 action_confirm（draft→pending→confirmed）
                                      【成团前置校验：booked_seats ≥ min_seats 或人工保本发团】
订单状态：已成团/待出发              通知游客（短信/邮件 P2）
    ↓
                                   → 计调操作 action_operate（派导/派车/订房/订餐/门票，BS-03）
    ↓
                                   → 出团 action_start（confirmed/operating→in_progress）
订单状态：已出行
    ↓
                                   → 回团 action_complete（in_progress→completed）→ 结算/归档
订单状态：已完成
```

> **关键对齐点**：游客侧「订单状态」由后端 `tour.plan.state` + 收款状态驱动（见 §5）。财务唯一口径始终在 `tour.plan`；`sale.order` 只做在线销售/收款入口，不独立出账（TDS-PROD-001 §4.2）。

### 4.2 家庭/多人报名

```
选班期 → 填成人数/儿童数/老人数/学生数/婴儿数 → 逐人证件子表（tour.plan.reg.passenger）
→ 校验：证件每人必填、类型合法、身份证 15/18 位
→ 计价：五档价 × 人数（老人/学生/婴儿价回退 tour.line）
→ 建 reg（guest_count = Σ人数 − baby_num）
→ 余位回写 += 总人数（含婴儿占位）
```

> 婴儿（baby）**占余位**但**不计有效客人数**（guest_count 排除），与实际占位一致；证件用出生证明/户口本（id_type=other）。

### 4.3 团队包团（BizMode=1）

```
客户询价（单位/会议/研学，定制日期+人数+协议价）
    ↓
销售在后台建 tour.plan（plan_type='1' 团队、biz_mode='1'、协议价、supplier_id=客户档案）
    ↓
（或 CRM 线索 → 赢单 → action_convert_to_plan 转 draft 团，回写 lead_id）
    ↓
审核 → 收款 → 计调 → 出团 → 结算（同散客后端链路，跳过并团）
```

> 包团**不参与散客并团**；人数/房型/接送按整团需求录入；金额走协议价（`out_price_quo_sum` 可用于组团报价，收入仍落 `in_com_quo_sum`）。

### 4.4 代订（BizMode=41）

```
客户单订一项服务（房/签/票/餐/车/险）
    ↓
后台建 tour.plan（biz_mode='41'、plan_type='5'）→ 建 reg
    ↓
代收代付：sum_money_delegate / sum_pay_delegate 独立核算（BS-06 §六）
    ↓
不参与并团、不进入计调派车派导（单项服务直接对接供应商）
```

### 4.5 自由行（BizMode=51/52）

```
机+酒套餐作为线路 product（tour.line）
    ↓
一组客人拆多订单（51，main_reg_id 指向主报名单）/ 多组客人共享服务（52）
    ↓
订单间以 main_reg_id 关联，主报名单统领结算
```

### 4.6 改签（改班期 / 改人数 / 改房型）

```
游客/销售发起改签（出团前）
    ↓
改班期（同线路）：校验新班期 published 且 remain_seats ≥ 改后人数
    ├─ 释放原班期余位（booked_seats -= 原人数）
    ├─ 占用新班期余位（新班期 booked_seats += 人数）
    ├─ 重算价差（新班期五档价 − 原价）→ 补收/退还
    └─ 记录 tour.plan.change（change_type='改班期'，留痕）
改人数/房型：触发重新计价（BS-02 §7.4），记录变更
    ↓
跨线路改签 = 原单退订（按违约金）+ 新单报名（两条独立记录，不可原位覆盖）
```

> **改签约束**：已出团（in_progress）/已归档不可改；改签不触发退订违约金，但已产生的实际损失（机票/签证）按票证实扣。

### 4.7 退订（取消 / 退款 / 违约金）

```
游客/销售发起退订（出团前）
    ↓
计算违约金（按 §6.6 退改政策，距出发天数分档 + 实际损失实扣）
    ↓
释放余位：tour.departure.booked_seats -= 退订人数（★当前缺失，必须补）
    ↓
reg 取消：reg_state = cancelled；plan 人数/金额 _sync_amounts_from_regs 重算
    ↓
退款：应退 = 已收款 − 违约金 − 实际损失
      → 走 BS-06 退款（sum_money_return 应退 / sum_pay_return 已退，支持负数红冲）
    ↓
整团退订（散客团全员退）：plan → cancelled / refunded；班期余位全释放
    ↓
通知游客退款到账（P2）
```

## 5. 状态机设计（核心）

### 5.1 游客侧订单状态机 `customer_state`（7 态，新增）

> 游客在 C 端看到的订单状态。作为 `tour.plan.reg` 上的存储字段（`store=True`，由后端动作/收款状态驱动），电商路径同步映射到 `sale.order` 的展示。

```
待支付(1) → 已支付/待确认(2) → 已成团/待出发(3) → 待出发(4) → 已出行(5) → 已完成(6)
    │                │              │                                   ↑
    └──→ 已退订(7) ◄──┴──────────────┴───────────────────────────────────┘
         （任意「已出行」前状态可退订；已出行后不可退，走「行程中止/理赔」）
```

| 值 | 状态 | 含义 | 触发 |
|----|------|------|------|
| 1 | 待支付 | 已下单未付款 | 下单成功，sum_pay_normal=0 |
| 2 | 已支付/待确认 | 已付款，等销售确认 | 在线支付成功 或 线下收款认领审核通过 |
| 3 | 已成团/待出发 | 计调确认成团 | plan.state=confirmed |
| 4 | 待出发（临近） | 计调操作中，临近出发 | plan.state=operating |
| 5 | 已出行 | 出发进行中 | plan.state=in_progress |
| 6 | 已完成 | 回团结算 | plan.state=completed |
| 7 | 已退订 | 取消/退款 | plan.state ∈ {cancelled, refunded} 或 reg_state=cancelled |

### 5.2 后端状态机（现状 + 建议补齐）

**`tour.plan.state`（团，10 态，已实现）**：

```
draft → pending → confirmed → operating → in_progress → completed → archived
任意状态可：cancelled / refunded / void
```

**`tour.plan.reg.reg_state`（报名，新增，建议补齐）**：

```
draft(草稿) → confirmed(已确认) → cancelled(已取消) / refunded(已退款)
```

> 现状：reg **无独立 state**，只靠 `audit_chk/verify_chk` 布尔 + 跟随 plan。补 `reg_state` 的动机：报名单是游客下单的载体，需要独立可退订/可取消的最小状态，否则「单笔报名退订释放余位」无处挂状态。

**`tour.departure.state`（班期，3 态，已实现）**：`draft → published → ended`

**`sale.order.state`（电商，标准）**：`draft → sent → sale(已确认) → done(已锁定) / cancel`

### 5.3 两侧映射与驱动动作

| 游客侧 customer_state | 后端驱动源 | 驱动动作（dev-odoo 实现点） |
|----------------------|-----------|---------------------------|
| 1 待支付 | reg 创建 + sum_pay_normal=0 | `_create_plan_reg_from_order` 建单 |
| 2 已支付/待确认 | plan=draft/pending + 收款已认领 | `tour.payment.claim` 认领审核通过回写 sum_pay_normal |
| 3 已成团/待出发 | plan=confirmed | `plan.action_confirm()`（计调确认成团） |
| 4 待出发 | plan=operating | `plan.action_operate()`（计调中） |
| 5 已出行 | plan=in_progress | `plan.action_start()`（出团） |
| 6 已完成 | plan=completed | `plan.action_complete()`（回团） |
| 7 已退订 | plan=cancelled/refunded 或 reg_state=cancelled/refunded | `reg.action_cancel()`（释放余位+违约金） / `plan.action_cancel/refund` |

**对齐规则**：

1. **团退订 → 报名全退**：`plan.action_cancel()` 级联所有 `reg_state=cancelled`，释放对应班期全部余位。
2. **单笔退订 → 团不退**：仅该 `reg` 退，释放该笔人数余位，`plan` 金额/人数 `_sync_amounts_from_regs` 重算。
3. **支付状态是游客侧 1→2 的唯一闸口**：`sum_pay_normal > 0` 才允许进入「已支付」；财务口径以 `tour.plan.sum_pay_normal` 为准。
4. **成团是游客侧 2→3 的唯一闸口**：`plan.action_confirm()` 前必须过 §6.2 成团校验。

## 6. 业务规则清单

> **规则默认值已拍板（2026-09-14，tour-ba）**：下列默认值基于旅行社行业惯例、易途系统参数与业务常识直接定案，不再留待决策；按「全局 → 线路 → 班期」三级可配置，逐级覆盖。

### 6.0 业务规则默认值与可配置字段总表

**（一）默认值总表**

| 规则项 | 默认值 | 拍板理由 |
|--------|--------|---------|
| 成团阈值 min_seats | **16 人** | 散拼最小常用车型为 16 座中巴，满 16 人即覆盖车辆成本、低于则大概率亏本；散客拼团行业通用成团线（8/10/16 中取 16 保本） |
| 成团截止 confirm_deadline_days | **出发前 2 天** | 给计调留足确认成团/退改/派车导时间，又不至于过早封团错过收客；国内散拼通用 1~2 天取 2 |
| 证件补录时限 | 出境 **15 天**／机火票 **7 天**／保险 **3 天**／国内 **1 天** | 签证办理周期最长（护照+签证 10~15 天）；实名出票需提前锁定；实名投保提前 1~3 天取 3 给缓冲 |
| 退订违约金梯度 | ≥7 天 **0%**／3~7 天 **20%**／1~3 天 **50%**／<24h **100%**，另实际损失凭票实扣 | 行业标准退改梯度（《旅行社条例》及主流 OTA 通用），越临近出发占位损失越大 |
| 未成团默认处理 | **自动取消退款**（auto_cancel） | 游客侧确定性高（不被吊着等）、财务干净（原路退款）、降低计调人工；转散客并团/手动为计调可切换项 |
| 改签规则 | 同线路改班期**免费**（仅重算价差）；跨线路改签=**退订+新报**（按违约金） | 同线路改班期不产生额外损失，行业惯例免费；跨线路等同重新购买，按退订规则处理 |

### 6.2 成团阈值规则（新增，核心）

**默认值（已拍板）**：`min_seats=16`（最低成团人数，0=一人成团/保本发团）；`confirm_deadline_days=2`（出发前 2 天成团截止，0=不限）。三级配置：全局 `tour.default_min_seats=16`/`tour.default_confirm_deadline_days=2` → 线路 `tour.line.default_min_seats`/`default_confirm_deadline_days` → 班期 `tour.departure.min_seats`/`confirm_deadline_days`（可覆盖）。

| # | 规则 |
|---|------|
| R-07 | 到出发前 `confirm_deadline_days` 天，若 `booked_seats ≥ min_seats`，系统提示计调可「确认成团」；若 `< min_seats`，按 `ungroup_action` 默认策略执行（见 R-08） |
| R-08 | 未成团处理：默认 `auto_cancel`（系统自动取消团→级联退报名→释放余位→原路退款→通知游客）；计调可在截止前切换为 `merge`（转散客并团到其他已成团班期，需选定目标班期）或 `manual`（保本/亏本发团须填原因、高权限、留痕；或改期继续收客） |
| R-09 | `min_seats=0` 的班期视为「一人成团」，可直接确认 |
| R-10 | 「确认成团」动作 = `plan.action_confirm()`，触发游客侧状态 2→3 并通知游客 |

### 6.3 证件要求与时限（新增）

**默认值（已拍板）**：证件收齐时限按团类型分档——出境 **15 天**、机火票 **7 天**、保险 **3 天**、国内常规 **1 天**。`id_required` 出境/机火票/保险团自动置 True（可人工改），国内常规团默认 False（建议收证）。`id_deadline_days` 按线路类型自动推导默认，可在线路级覆盖；0=不限。

**可配置字段**：`tour.line.id_required`（Boolean 是否必须收齐证件）、`tour.line.id_deadline_days`（Integer 出发前 N 天收齐）、`tour.line.id_note`（Text 证件说明）；全局分档参数 `tour.id_deadline.abroad=15`/`air_rail=7`/`insurance=3`/`domestic=1`。

| 团类型 | 必须收证件 | 证件种类 | 提前时限（默认） |
|--------|:----------:|---------|:-------------------:|
| 出境团（is_abroad / is_jw） | ✅ | 护照 + 身份证 | 出发前 15 天（签证） |
| 含机票/火车票团 | ✅ | 身份证（实名出票） | 出发前 7 天 |
| 含保险团（实名投保） | ✅ | 身份证 | 出发前 3 天 |
| 国内常规团 | ⚠️ 建议 | 身份证 | 出发前 1 天 |
| 婴儿/儿童 | ✅ | 户口本/出生证明（id_type=other） | 同成人 |

| # | 规则 |
|---|------|
| R-11 | `id_required=True` 的团，报名时逐人证件必填（`tour.plan.reg.passenger`），缺证不可提交 |
| R-12 | 出发前 `id_deadline_days` 天仍未收齐证件 → 系统生成「催办证件」任务（计调/销售），并可在出团前置校验中预警 |

### 6.6 退订违约金规则（新增，可配置）

**默认值（已拍板）**：采用行业标准四档梯度（0%/20%/50%/100%）作为**系统默认退改政策**，另叠加实际损失实扣；线路可挂自定义 `tour.cancel.policy` 模板覆盖（如「特价不退」100% 不退）。

**可配置字段**：`tour.cancel.policy`（退改政策模板：距出发天数区间 → 违约金比例），`tour.line.cancel_policy_id`（M2O，默认挂系统内置「默认退改政策」）。

| 距出发时间 | 违约金比例（默认） | 说明 |
|-----------|:------------------:|------|
| ≥ 7 天 | 0% | 全额退 |
| 3~7 天（含 3 不含 7） | 20% | |
| 1~3 天（含 1 不含 3） | 50% | |
| < 24 小时（<1 天） | 100% | 不退团款 |
| 已产生实际损失 | 损失实扣 + 手续费 | 机票/签证/房费凭票据实扣，不受比例上限约束 |

| # | 规则 |
|---|------|
| R-24 | 应退金额 = 已收款 − 违约金（按比例）− 实际损失（凭票证实扣），结果 ≥ 0 |
| R-25 | 已出行（in_progress 后）不可退订，走「行程中止/理赔」另行处理 |
| R-26 | 退款走 BS-06：`sum_money_return`（应退）/`sum_pay_return`（已退），支持负数红冲；退款金额 ≤ 已收款 |
| R-27 | 退订**必须释放余位**（`booked_seats -= 退订人数`）——★当前代码缺失 |
| R-28 | 整团退订级联所有报名退订 + 班期余位全释放 + plan → cancelled/refunded |
| R-29 | 退订留痕：操作人/时间/违约金/实扣明细写 `tour.plan.change`（change_type='退订'）或 `remark` |

### 6.7 改签规则

**默认值（已拍板）**：改签不收费。同线路改班期（含改人数/房型）**免费**，仅重算价差（补收/退还）+ 已产生实际损失实扣；跨线路改签 = 原单退订（按 §6.6 违约金）+ 新单报名。改签手续费默认 0，线路级可配置 `tour.line.reschedule_fee`（Float，默认 0）。

| # | 规则 |
|---|------|
| R-30 | 改班期（同线路）：先释放原班期余位，再占用新班期余位（重校验 remain_seats） |
| R-31 | 改签重算价差：新价 − 原价 > 0 补收；< 0 退还；价差与违约金分列核算 |
| R-32 | 改签不触发退订违约金、不收改签费（`reschedule_fee=0`）；但已产生的实际损失实扣 |
| R-33 | 改签留痕：`tour.plan.change`（change_type='改班期'/'增人'/'减人'/'改房型'），`first_plan_id` 指向原团溯源 |
| R-34 | 已出团（in_progress）/已归档不可改签；跨线路改签 = 退订（按违约金）+ 新报两条记录 |

## 8. 数据一致性（单一事实源）

| 数据 | 单一事实源 | 派生/冗余 | 规则 |
|------|-----------|----------|------|
| 余位 | `tour.departure.booked_seats` | `remain_seats` = seats − booked_seats（compute） | 报名 +N、退订 −N、改签先减后加；`@api.constrains booked_seats<=seats` 兜底 |
| 报名明细金额 | `tour.plan.reg.in_com_quo_sum` / `sum_un_pay` | — | 下单快照，调价不回溯 |
| 团金额/人数 | `tour.plan`（`_sync_amounts_from_regs` 幂等 Σregs） | 团视图金额 = Σ 报名 | 任何报名增删改后重算，**不得叠加** |
| 收款 | `tour.plan.sum_pay_normal` | reg.sum_pay_normal（认领回写） | 认领审核通过回写（BS-06） |
| 并团归属 | `reg.first_plan_id` / `reg.plan_id` | — | 并团 = 改写指针 + `tour.merge` 留痕 |
| 财务口径 | `tour.plan`（唯一） | `sale.order` 只做入口 | 电商不独立出账（TDS-PROD-001 §4.2） |

**一致性红线**：

1. 余位、人数、金额三者的任何变更都必须落回 `tour.departure.booked_seats` 与 `tour.plan` 汇总（单一事实源），禁止在 reg 与 plan 之间出现双份可漂移的余额。
2. 退订/取消/改签必须「先释放余位 → 再改状态 → 再重算团汇总」三步原子完成（同一事务）。
3. 并团只改 `first_plan_id` 指针，不复制报名记录，避免同一客人出现两份报名。

| AC-17-08 | 改签释放+占用余位 | 原班期余位 +N，新班期余位 −N，价差补收/退还正确，`tour.plan.change` 留痕 |
| AC-17-09 | 已出团不可改签/退订 | in_progress 订单执行改签/退订报错 |
| AC-17-10 | 证件必收团缺证拦截 | id_required=True 的团，报名缺任一客人证件 → 报错不可提交 |
| AC-17-11 | 证件催办任务 | 出发前 id_deadline_days 天未收齐证件 → 生成催办任务 |
| AC-17-12 | 多类型家庭报名计价 | 2 成人 1000 + 1 老人 800 + 1 婴儿 0 → in_com_quo_sum=2800，guest_count=3（不含婴儿） |
| AC-17-13 | 散客并团复用承载团 | 同班期 3 笔报名 → 同一 tour.plan，reg_code 独立，团金额 = Σ3 笔（幂等） |
| AC-17-14 | 团金额幂等重算 | 增/减报名后 _sync_amounts_from_regs 重算不叠加 |
| AC-17-15 | 包团跳过并团 | BizMode=1 建团后报名 first_plan_id=自身，不参与散客并团 |
| AC-17-16 | 财务唯一口径 | 电商 sale.order 确认后，收款/收入只在 tour.plan 层出账，sale 层不重复记账 |
| AC-17-17 | 并发防超卖 | 余位 1，两并发报名各 1 人 → 仅 1 成功，1 报「余位不足」 |
| AC-17-18 | 客户查询隔离 | 凭「报名单号+手机号」只能查本人报名 |
