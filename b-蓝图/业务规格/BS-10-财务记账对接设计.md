## 一、文档定位与设计原则

### 1.1 定位

本文件定义 **tour_finance 如何用 Odoo 原生会计引擎（account）记账**，是 BS-05~08 的"落账层"设计：

- BS-05~08 定义"业务层"（收款认领、对账、佣金、科目体系、分录模板）；
- **BS-10 定义"记账层"**：把业务层映射到 `account.account` / `account.move` / `account.payment` / `account.move.line` / `account.analytic.account` / `account.reconcile`，并给出每类业务的**可执行复式分录模板**（借贷行 + 科目编码 + 辅助核算 + 分析账户 + 合规标注）。

dev-odoo 拿到本文件即可直接写 `data/*.xml`（科目/日记账）、模型扩展（字段、生成 `account.move` 的方法）与校验。

### 1.2 设计原则（定调）

> 用户定调：**财务模块尽量用 Odoo 原生财务逻辑（account 复式记账/科目/日记账/核销/分析账户），而不是自造金额字段。**

| # | 原则 | 含义 |
|:--:|------|------|
| P1 | 复式记账不自己造 | 一切金额流转都落到 `account.move`（借贷平衡），`tour.plan` 上的 `in_sum/out_sum/sum_pay_normal/...` 只作**业务口径快照**，不作记账依据 |
| P2 | 科目用 l10n_cn | 科目表以 Odoo `l10n_cn`（中国企业会计准则科目表）为基准，旅行社专用明细科目在其上扩展 |
| P3 | 单团核算用 analytic | 用原生 `account.analytic.account` 作"一团一核算"维度，凭证行挂分析账户 |
| P4 | 核销用原生 reconcile | 应收/应付核销走 `account.move.line` + `account.full.reconcile`/`account.partial.reconcile` |
| P5 | 旅行社特有逻辑保留独立模型 | 收款认领规则（tour.payment.claim）、往来对账（tour.reconciliation）、佣金个税计算（tour.commission）是旅行社特有，保留自建模型，但**结果都生成原生 account 单据** |
| P6 | 每条凭证标准则依据 | 每张凭证/每个明细行标注合规依据（CAS 14/22/个税法/财税2016-36号等） |

### 1.3 关键决策总览

| 决策 | 结论 | 章节 |
|------|------|------|
| D1 科目表基准 | l10n_cn（企业会计准则科目表），tour 扩展明细科目 | §四 |
| D2 差额征税标记 | 在 `account.account` 上新增 `tour_vat_deductible` 布尔字段（按科目固定标记可扣除/不可扣除） | §4.6 |
| D3 单团核算 | 推荐 Odoo 原生 analytic 维度，`tour.plan.account` 保留为"团级核算台账" | §六 |
| D4 收款认领 | `tour.payment.claim` 保留（认领规则特有），认领审核后生成 `account.payment` | §8.4 |
| D5 对账 | 核销用原生 reconcile；`tour.reconciliation` 保留做 11 类**往来对账**（发票归集/印花税/二次结算） | §8.5 |
| D6 佣金个税 | `tour.commission` 保留计算（个税/分成特有），确认/发放生成 `account.move` | §8.6 |
| D7 合规标注 | `account.move` 新增 `compliance_ref`（主标签）+ `account.move.line` 新增可选标签 | §九 |
| D8 依赖升级 | `tour_finance.__manifest__.py` 的 `depends` 增加 `account`、`analytic`（`l10n_cn` 作为推荐安装项） | §8.0 |

## 二、现状盘点与基础设施

### 2.1 Odoo account 现状

| 项 | 现状 | 影响 |
|----|------|------|
| 科目表 | 通用国际科目表（51 科目），**非**中国企业会计准则 | 无法直接用于 CAS 报表列报，必须换/叠加 l10n_cn |
| 日记账 | 6 本（销售/采购/银行/现金/杂项等默认） | 需补充微信/支付宝等第三方资金日记账 |
| l10n_cn | **安装中** | 提供企业会计准则科目表 + 财税报表框架 |
| 增强套件 | 已存在 `base_accounting_kit`（Cybrosys，Odoo 19 Community 财务增强：报表/资产/预算/银行对账） | 提供利润表/资产负债表/总账/往来账龄/银行对账能力，Community 下会计能力可用 |

### 2.2 落地方式

1. **科目表**：以 `l10n_cn` 安装产生的企业会计准则科目为一级/二级，tour_finance 通过 `data/tour_chart_of_account.xml` 追加旅行社明细科目（§四）。
2. **不删除/不改名 l10n_cn 现有科目**，只做"继承 + 新增明细 + 设置 reconcile/analytic/差额标记"。
3. **单据**：`tour_finance` 的 6 个模型升级为 `account`/`analytic` 的消费者与触发器（§八）。

## 四、会计科目体系设计（映射 l10n_cn）

### 4.1 设计规则与 account_type 映射

- 编码遵循《企业会计准则——应用指南》科目表（4 位一级，明细用 `.NN` 或扩展位）。
- `reconcile=True`（辅助核算）挂在往来/资金科目上，用于原生核销。
- 收入/成本科目开启 analytic（`account.analytic.account` 维度），供单团核算。
- 成本科目按 `tour_vat_deductible` 标记差额征税可扣除性（§4.6）。

Odoo `account_type` 与科目类别对照：

| CAS 类别 | Odoo account_type |
|----------|-------------------|
| 货币资金 | `asset_cash` |
| 应收/其他应收 | `asset_receivable` |
| 预付/坏账准备（备抵） | `asset_current`（坏账准备作备抵科目，余额方向相反） |
| 应付/其他应付/预收 | `liability_payable` / `liability_current`（预收用 `liability_current`） |
| 应交税费 | `liability_current` |
| 主营/其他业务收入 | `income` / `income_other` |
| 主营/其他业务成本 | `expense_direct_cost` |
| 期间费用 | `expense` |
| 资产减值损失/营业外支出 | `expense` |

### 4.5 差额征税标记字段设计（D2）

在 `account.account` 上扩展一个布尔字段（按科目固定标记，最简单且一致）：

```python
class AccountAccount(models.Model):
    _inherit = 'account.account'
    tour_vat_deductible = fields.Boolean(
        '差额征税可扣除', default=False,
        help='[财税2016-36号] 旅游服务差额征税：住宿/餐饮/交通/门票/地接/签证费可扣除；'
             '导服/保险/自费/购物不可扣除')
```

- 归属：科目级（6401.01~06 及对应 2202.01~06 为 True；6401.07~10 为 False）。
- 用途：增值税差额申报时 `SUM(可扣除科目借方发生额)` 作为扣除项归集依据（配合 BS-05 §2.1 的 `invoice_money`/`un_invoice_money` 发票缺口，无票部分不参与扣除）。

## 五、日记账设计

| 日记账 | type | 用途 | 备注 |
|--------|------|------|------|
| 现金日记账 | cash | 1001 库存现金收付 | 现金限额控制 |
| 银行日记账（各账户一本） | bank | 1002 银行存款收付 | 每 `tour.bank.account` 对应一本（§8.1） |
| 其他货币资金—微信 | bank | 1012.01 收付 | 微信 |

## 六、单团核算方案（D3：推荐 analytic 维度）

### 6.1 结论

**推荐：以 Odoo 原生 `account.analytic.account` 作为"一团一核算"的记账维度；`tour.plan.account` 保留为团级核算台账（税务 + 管理聚合），两者通过 `analytic_account_id` 连接。**

理由：

| 考量 | analytic 维度 | 自建 tour.plan.account 单独算 |
|------|--------------|-------------------------------|
| 记账完整性 | ✅ 凭证行直接挂团，借贷平衡、可追溯 | ❌ 需另起一套金额台账，与总账易脱节 |
| 单团利润表 | ✅ `analytic` 报表/分组视图原生出 | ❌ 自建 compute |
| 差额征税归集 | ❌ analytic 不原生区分可扣除/不可扣除 | ✅ tour.plan.account 专有字段 |
| 发票缺口 | ❌ 不原生 | ✅ tour.plan.account 专有字段 |
| 团级状态机/归档 | ❌ 不原生 | ✅ tour.plan.account |

**结论**：二者**互补而非二选一**——analytic 负责"账"，tour.plan.account 负责"台账（税/管理）"。

### 6.2 分工定义

| 职责 | 归属 | 说明 |
|------|------|------|
| 团级收入/成本记账 | `account.analytic.account` | 每张收入/成本/佣金凭证行挂 analytic_account_id |
| 单团利润（账面） | analytic 分组聚合 | `income - expense`（按团） |
| 差额征税可扣除/不可扣除 | `tour.plan.account` | `cost_deductible`/`cost_non_deductible` |
| 发票缺口 | `tour.plan.account` | `invoice_gap`（← plan.un_invoice_money） |
| 团级利润（含/不含购物） | `tour.plan.account` | `profit`/`profit_no_shop` |
| 团级状态（核算中/已结算/已归档） | `tour.plan.account` | `state` 状态机 |
| biz_mode（总额/净额法判定） | `tour.plan.account`（related plan.biz_mode） | 决定收入确认方法 |

### 6.3 analytic account 设计

- **命名**：`plan_code` 即分析账户名（如 `TD20260912-01`）；`tour.plan.account.analytic_account_id` 建团时自动创建。
- **维度标签**（`account.analytic.distribution` 或 `analytic.tag_ids` 可选）：业务模式（biz_mode）、部门（department_id）、线路（line_id）。
- **生成时机**：`tour.plan` 确认发团（或创建 tour.plan.account 台账）时自动创建/关联 analytic account。
- **约束**：`tour.plan` 与 analytic account 1:1（`tour.plan.account` 已有 `_uniq_plan` 约束保证）。

```python
class AccountMoveLine(models.Model):
    _inherit = 'account.move.line'
    compliance_ref = fields.Selection(<同上>, string='准则依据(行级)',
        help='凭证跨多准则时按行覆盖主凭证标签；默认继承 account.move.compliance_ref')
```

- 凭证级 `compliance_ref` 为**必填**（生成凭证的方法里传入）；行级可选覆盖（用于 §7.4.2 这类一凭证跨 CAS 9 + 个税法 的场景）。
- 摘要：`account.move.narration` 统一写 `[团号][客户/供应商][业务场景]`，如 `TD20260912-01 / 张三 / 收款认领核销`。
