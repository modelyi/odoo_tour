## 1. 业务背景

订单是旅行社业务的核心载体，承载「客户报名 → 确认/并团 → 计调执行 → 财务结算」全流程。海螺旅行社在易途系统中累计产生 **86,925 条团队订单**（137 字段）与 **86,753 条订单报名**（77 字段）。

### 1.1 四类核心业务形态（按真实数据占比排序）

| 形态 | BizMode | 条数 | 占比 | 说明 |
|------|---------|-----:|-----:|------|
| **团期计划（先计划后报名）** | 12 | 56,592 | 65% | 先建发团计划（含同行价/余位），再收客报名。**系统绝对主线** |
| **散客并团（先报后并）** | 15(21,769) / 14(708) | 22,477 | 26% | 散客先各自报名，再并入同一发团计划统一计调 |
| **代订项目** | 41 | 4,410 | 5% | 单项代订（门/房/签/票/餐/车/险/收/支/导） |
| **团队输单（团队直订）** | 1 | 2,544 | 3% | 团队客户整团直接下单，跳过并团 |
| 散客单组 | 13 | 895 | 1% | 独立散客组 |
| 自由行 | 51 | 6 | <0.1% | 机+酒套餐/多订单组合（量小但结构特殊） |

> 关键认知修正：v1.0 把「散客并团（先报后并）」当作主线流程。**真实数据里 65% 的订单是「团期计划（先计划后报名）」**，并团只是 26% 的散客场景的收尾动作，不是全局主线。

### 1.2 业务痛点

1. **并团逻辑复杂**：散客并团、关键字并团、自由行多订单并存，v1.0 误用 MainRegID 建模，与真实数据脱节
2. **金额口径混乱**：报价/收款/未收/退款/代收 15+ 个金额字段，主字段识别错误（outPrice_QuoSum vs SumPay_Normal vs InCom_QuoSum）
3. **字段冗余**：137 字段实际使用率不足 40%，大量字段全空（InvoiceMoney、SumDeposit、PreCost_QuoSum 等）
4. **导游 PII 泄漏**：guidelist 内嵌导游身份证/手机明文，是最大数据安全红线
5. **收款认领**：财务先收款后认领（收款登记 51 条 vs 订单 86,925 条），匹配困难
6. **变更溯源**：单团变更靠团号 `[变更-N]` 后缀 + 同 RegCode 溯源，无结构化变更记录

## 3. 业务流程

### 3.1 团期计划流程（主线，BizMode=12，占 65%）

```
产品经理创建发团计划（选择线路、设出发日期/余位/同行价）
    ↓
发布计划（同业/门市可见）
    ↓
销售为客人创建报名单（关联发团计划）
    ↓
系统自动计价（客人类型 × 单价）
    ↓
确认报名（生成 RegCode）
    ↓
收款确认（财务认领到订单）
    ↓
计调操作（派车/派导/订房/订餐）
    ↓
出团执行 → 回团结算 → 归档
```

### 3.2 散客并团流程（BizMode=14/15，占 26%）

```
散客 A/B/C 各自报名（生成独立 RegCode、独立计价、独立收款）
    ↓
并团操作：将多个报名单挂到同一发团计划（写入 FirstPlanID）
    ↓
系统合并客人名单、房型汇总
    ↓
统一计调操作（一辆车/一名导游）
    ↓
按报名单独立结算（价格、收款、返款各自独立）
    ↓
出团执行 → 回团 → 归档
```

### 3.3 团队输单流程（BizMode=1，占 3%）

```
团队客户定制需求 → 创建团队订单（选择线路、日期、人数、协议价）
    ↓
计价（团队协议价）→ 审核 → 收款 → 计调 → 出团 → 结算 → 归档
```

### 3.4 自由行流程（BizMode=51/52）

```
客人预订自由行套餐（机+酒）
    ↓
一组客人可拆成多个订单（51）/ 多组客人共享服务（52）
    ↓
订单间通过 MainRegID 关联（主报名单）
```

### 3.5 订单状态流转（目标状态机 + 源状态映射）

**目标状态机（新系统设计）**：

```
草稿(Draft) → 待确认(Pending) → 已确认(Confirmed) → 计调中(Operating)
    → 出行中(InProgress) → 已完成(Completed) → 已归档(Archived)

特殊状态（任意阶段可达）：
- 已取消(Cancelled)：记录原因
- 已退款(Refunded)：退款完成
- 作废(Void)：删除/作废
```

**源系统 State 字段实测分布与迁移映射（best-effort，低置信项已标注）**：

| 源 State | 条数 | 关联特征 | 建议映射 | 置信度 |
|---------|-----:|---------|---------|--------|
| 5 | 75,742 | AuditChk=True，历史主数据 | 已确认/已完成 | 🟡 中 |
| 6 | 7,191 | VerifyChk=True（已核销） | 已完成 | 🟢 高 |
| 3 | 3,258 | AuditChk=False | 待确认/待审核 | 🟡 中 |
| 0 | 314 | 接送站/草稿类 | 草稿 | 🟡 中 |
| 4 | 224 | — | 计调中 | 🟡 低 |
| 1/2 | 179 | 保险/费用类 | 待处理 | 🟡 低 |
| 99 | 14 | 2024 年数据 | 作废/删除 | 🟢 高 |

> 源 `State` 语义未完全确定（仅 6/99 可高置信确认），迁移时需逐值复核，不建议机械映射。

## 4. 并团逻辑详细说明（核心修正）

### 4.1 结论先行

**散客并团的真实数据模型是「FirstPlanID 指针」，不是「MainRegID 主报名单」。**

- `plan_regs.MainRegID`：86,753 条中仅 **6 条非 0**，且全部 `BizMode=51`（自由行）。**它只服务自由行的「主报名单」关联，与散客并团无关。**
- `team_orders.FirstPlanID`：86,925 条中 **86,611 条非 0（99.6%）**。它是「订单首次挂接的发团计划」指针，散客并团就是把多个报名单的 FirstPlanID 指向同一个发团计划。

### 4.2 FirstPlanID 机制

```
tour.plan (发团计划/团队订单)
   ├─ plan_code = "ZY-200101S-1"（团号）
   ├─ first_plan_id = 64（首发计划，指向自身或变更前的原始计划）
   └─ ← 多个报名单指向它

tour.plan.reg (报名单)
   ├─ reg_code = "ZY200101SP-3"（报名单号）
   ├─ plan_id = 64（当前所属发团计划）
   └─ first_plan_id = 64（首次挂接的发团计划，并团后指向合并目标）

并团操作 = 把 N 个报名单的 first_plan_id / plan_id 从各自的原始计划
          改写为同一个「合并目标计划」
```

**FirstPlanID 的三种语义**：

| 场景 | first_plan_id 取值 | 说明 |
|------|-------------------|------|
| 团期计划/团队直订 | = 自身 PlanID | 计划即源头，无前置计划 |
| 散客并团 | = 合并目标计划 PlanID | 报名单并入哪个计划，就指向哪个计划 |
| 单团变更 | = 变更前的原始计划 PlanID | 变更团 `[变更-N]` 版本仍指向未变更的原始计划，实现溯源 |

### 4.3 三种并团模式

| 模式 | 触发 | 机制 | 结算方式 |
|------|------|------|----------|
| **散客并团（DSN 14/15）** | 多个散客报名单合并到同一发团计划 | 报名单 `first_plan_id` 指向同一计划 | 报名单独立结算（价格/收款/返款各自独立） |
| **关键字并团（18）** | 行程以「选择线路」形式添加 | 按线路名称+日期自动匹配合并 | 碎片化行程拼接 |
| **自由行并团（51/52）** | 一组客人多订单/多组客人多订单 | 通过 `main_reg_id` 指定主报名单 | 主报名单统领结算 |

### 4.4 并团约束（业务规则）

1. 仅「散客类」模式（DSK 12 / DSS 13 / DSN 14,15）的报名单可并团；团队输单（1）、代订（41）不参与并团
2. 并团后各报名单保留独立 `reg_code`、独立金额（`sum_pay_normal` 等），仅计调资源（车/导/房）合并
3. 并团必须记录 `tour.merge`（并团记录），含操作人/时间/并入名单快照，可审计、可回退
4. 自由行模式下 `main_reg_id` 才用于指定主报名单；其余模式 `main_reg_id` 恒为空

### 4.5 团号版本化（单团变更溯源）

单团变更在源系统中体现为**团号版本化**，而非独立变更表：

```
ZY-200507S-2          （原始团，PlanType=2）
ZY-200507S-2[变更-1]  （第 1 次变更，PlanType=7，first_plan_id 指向原始团）
ZY-200507S-2[变更-2]  （第 2 次变更，PlanType=7，first_plan_id 仍指向原始团）
        └── 共享同一 RegCode（ZY200507SP-70）
```

- `PlanType=7` 实测 5,309 条，其中 5,306 条（99.9%）团号带 `[变更-N]` 后缀
- 新系统应把变更团建成 `tour.plan.change` 记录（关联原团 plan_id），团号版本与 RegCode 双键溯源

## 6. 金额字段精确定义

| 打印 | 行程单、合同 | 模板可配置 |

### 7.7 核心业务规则汇总

1. **人数校验**：总人数 = AdultNum + ChildNum + OldManNum + BabyNum + StudentNum + GuideNum；GuestCount = 总人数 − BabyNum
2. **房型校验**：标准间×2 + 单间×1 + 三人间×3 + 加床×1 ≥ 成人数 + 占床儿童数
3. **日期校验**：EndDate ≥ BeginDate；PlanEndDate ≥ PlanBeginDate
4. **并团约束**：仅散客类模式可并团；并团后报名单金额独立、资源合并；并团须写 `tour.merge`
5. **变更约束**：已出团/已归档不可变更；变更团 `first_plan_id` 指向原团
6. **退款约束**：退款金额 ≤ 已收款金额；退款须关联原收款/原团队并审批；支持负数红冲
7. **权限隔离**：用户仅可见本公司/部门订单（OpCmpID/OpDptID）
8. **金额主字段**：已收款以 `SumPay_Normal` 为准，未收款以 `SumUnPay` 为准，报价以 `InCom_QuoSum` 为准

## 9. 敏感字段与安全分级

> 详细分级与财务衔接见《调研数据→产品设计需求补充说明》第三节。此处仅列订单模块相关项。

| 字段 | 安全等级 | 业务用途 | 可解密/查看角色 |
|------|---------|---------|----------------|
| guidelist 内导游身份证 IDNum（74,104 条明文） | 🔴 加密存储 | 个税代扣、保险、实名制 | 财务、系统管理员 |
| guidelist 内导游手机 Mobile（67,689 条明文） | 🟡 脱敏展示 | 派团联系 | 计调、销售 |
| guidelist 内银行卡 AccountNo | 🔴 加密存储 | 导游结算打款 | 财务 |
| 客人职业 GuestOccupation | 🟡 按权限展示 | 个性化服务/保险 | 销售、计调 |
| 联系人手机/座机/微信/地址 | 🟡 脱敏展示 | 联系客人 | 销售、计调 |

**三条硬性红线（P0）**：

1. **脱敏一致性**：同一实体同一 PII 在多表必须一致脱敏。当前 `guides.csv` 身份证已掩码，但 `team_orders.guidelist` 同批导游身份证/手机是完整明文——最严重泄漏点。
2. **禁止 JSON 内嵌 PII**：订单导游安排（guidelist）必须拆分为 `tour.operation.guide`，通过 GuideID 外键关联，冗余身份证/手机仅在确有业务用途且加密后保留。
3. **导出脱敏**：订单导出 Excel 时 PII 默认掩码，审批后导出完整值。
