## 1. 业务背景

计调是旅行社的运营中枢，负责把「已确认订单」转化为「可执行的资源安排」——即给某个团队订单落实导游、车辆、酒店、餐厅、门票，并确保资源不冲突、成本可控、出发前资源全部到位。

易途系统当前在「预定安排」菜单下用 **6 个独立操作台** 分散处理：导游安排、用房安排、用车安排、保险安排、地接安排，外加「预订安排」总入口，计调需反复切换页面，且导游/车辆安排**没有冲突检测**——同一导游/车辆同一天被重复派给两个团是常见事故。此外，用房/门票的预订确认在「营运中心」二次操作，与计调安排脱节。

业务痛点：
- 6 个独立页面反复切换，容易漏项，缺少「某团资源安排总进度」的统一视图
- 导游、车辆缺乏日期区间冲突检测，旺季重复派车派导频发
- 资源预订（房/门票）的确认状态与计调安排分离，资源是否到位不可见
- 各类资源预订数据同构度高，却用 6 套独立结构，模型冗余

**设计决策**：采用**通用预订模型 `tour.booking` + 资源类型区分**，替代旧版「操作台 + 7 个子模型」的拆分做法。理由：
1. 派导/派车/订房/订餐/门票在业务上是同一动作——「给团队订单在某个日期区间锁定一个资源对象」，差异仅在资源对象类型与几个类型专属属性；
2. 统一模型带来统一的冲突检测、统一的状态机、统一的看板统计；
3. 字段聚焦四大核心，避免过度设计。

**范围界定**：本规格聚焦 **派导、派车、订房、订餐、门票、保险、地接** 七大资源调度动作（门票合并进通用预订，保险/地接纳入 project.task 扩展）。以下不在本模块范围，另行处理：
- **导游借款 / 导游报账**：属财务收付款，划归 BS-05/BS-06；
- **二次结算**：与供应商的额外结算，属对账结算 BS-07。

### 3.1 tour.booking — 通用预订（核心模型）

**设计决策**：用单一 `resource_type` 区分资源类型，资源对象用「通用 `supplier_id`（res.partner）+ 类型专属 `guide_id`/`vehicle_id`」承载；类型专属字段仅在该类型下生效（nullable）。所有金额按类型语义映射（见字段说明），冲突检测统一作用于 `guide_id`/`vehicle_id`。

**易途源**：预订安排 / 导游安排 / 用房安排 / 用车安排 / 门票预订相关接口（`PlanGuide_Arrange`、`OrderHotelRquireList`、`OrderCar_Arrange`、`OrderScenicConfirm` 等）

**金额计算规则**（`amount_total` 默认值，可手工覆盖）：
- guide：`amount_total = guide_fee`
- vehicle：`amount_total = car_fee`
- hotel：`amount_total = room_price × night_num × (room_single + room_standard + room_triangle + room_accompany + room_additional)`
- meal：`amount_total = price_per_table × table_count`
- scenic：`amount_total = unit_price × (adult_num + child_num + old_man_num + student_num)`

## 4. 业务规则

### 4.1 资源冲突检测（核心）

> 目标：同一导游/同一车辆在同日期区间不能被安排给多个不同团队。

**冲突判定条件**（对 `tour.booking` 中 resource_type ∈ {guide, vehicle} 的记录）：

```
存在另一条 booking B，满足全部条件：
1. B.resource_type = 当前.resource_type
2. B.guide_id = 当前.guide_id   （guide 类型）或 B.vehicle_id = 当前.vehicle_id（vehicle 类型）
3. B.state ≠ cancelled
4. B.plan_id ≠ 当前.plan_id      （同团多段安排不算冲突）
5. 日期区间重叠：B.begin_date ≤ 当前.end_date AND B.end_date ≥ 当前.begin_date
```

**冲突处理**：
1. 保存/确认 booking 时触发检测，命中则**默认阻止**并弹出冲突警告（显示冲突的对方团号、日期区间）；
2. 具备「计调强制安排」权限的用户可**强制保存**，但必须填写强制原因（`remark` 或专用字段），操作写入日志留痕；
3. 单日资源（用餐、单日游览）`end_date = begin_date`，区间重叠退化为同日判定。

**不纳入冲突检测**：酒店、餐厅、景区（同一供应商可同时服务多团；酒店房量冲突属房量管理，一期不做）。

### 4.2 其他业务规则

1. **状态机**：`draft → confirmed → completed`，任意非 completed 状态可 `cancelled`；`confirmed` 前不产生结算义务。
2. **供应商类型约束**：`supplier_id` 必须匹配 `resource_type` 对应 sup_type（见 §3.2 表），不匹配保存时报错。
3. **未审核资源不可选**：`guide_id`/`vehicle_id` 仅可引用 `audit_chk=True` 的档案（沿用 BS-09 规则 9）。
4. **车辆座位校验**：`vehicle_id.seat_num`（正式座）< `plan.guest_count + plan.guide_num + 1`（司机）时预警「座位不足」，允许强制但需确认。
5. **房量一致性**：酒店 `room_standard` 等房型数默认从 `plan_id` 的房型汇总带入（`hotel_room_*`），可改。
6. **自动计算**：`night_num = end_date − begin_date`（酒店）；`amount_total` 按 §3.1 公式默认计算，可手工覆盖。
7. **二次确认**：`resource_type ∈ {hotel, scenic}` 的 booking 需营运中心将 `confirm_state` 置为 `confirmed` 后方视为「资源到位」。
8. **出团前置**：`tour.plan.action_start()` 出团时校验 5 项核心资源（guide/vehicle/hotel/meal/scenic 视线路是否需含餐）是否全部 `state=confirmed` 且房/门票 `confirm_state=confirmed`；未完成是否阻断由系统参数 `tour_operation.require_full_booking` 配置。
9. **权限隔离**：`tour.booking` 随 `plan_id` 继承 `company_id`/`department_id`，计调只能操作本公司/部门订单。

| 用户权限 | 计调按 company_id/department_id 隔离；强制安排、二次确认按角色授权 |

## 8. Odoo 映射建议

- **模型**：`tour.booking`（`_inherit = ['mail.thread', 'mail.activity.mixin']`）
- **视图**：tree（按订单/资源类型分组）、form、calendar（按 begin_date 展示，直观查冲突）、看板（计调看板，按 plan 聚合 5 项资源状态）

- **依赖模块**：tour_order、tour_resource、base
- **菜单**：计调操作 > 预订安排（booking 列表）、计调看板（plan 维度）
