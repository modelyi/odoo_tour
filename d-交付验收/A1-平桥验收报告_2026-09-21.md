## 4. 过程中的实测发现（都写进台账/已知问题）

### 4.1 addons 目录嵌套导致"健康检查通过但注册表残缺"（严重，已修）
`rsync -a tms-platform/addons tour-platform/addons` 产出 `tour-platform/addons/addons/…`，
容器仍返回 `/web/login` **HTTP 200**、healthcheck 通过，但日志里 `ERROR … Some modules are not loaded: [37 modules]`，
`n_models` 只有 615（正确值 758），`report.tour_accounting.report_general_ledger` 直接 `KeyError`。
→ 平桥拉平目录后恢复 758。
**结论：A2 的 healthcheck 必须校验注册表规模/模块加载，光看 200 会漏掉灾难性故障。**

### 4.2 冒烟动作在平桥库留下 2 个探针用户（将在末次 restore 时消失）
为跑"登录/权限"链路，在 `tour19` 建了 `a1_smoke_internal` / `a1_smoke_portal`（`tour-staging` 无 DNS，不能靠人肉点）。
删除受阻于 `hr_employee_user_id_fkey`：**新建 `res.users` 会自动产出一条 `hr.employee`**（OHRMS 行为，B2 迁移要注意）。
残留计数：`res_users +2`（90→92）、`pwd_hashed 329→331`、`ir_attachment +20`（10 `res.partner` + 10 `hr.employee`，id 28462 起 > 现网 max 28461）、filestore `+2` 文件。
→ **本报告的 0 差异判定以 §2 冒烟前的 recon 为准**；Gate A1 收尾按计划要做"冻结 → 末次 dump → 重灌 tour19 → 复测"，届时平桥库回到与现网逐键一致，探针残留自动清除。

### 4.3 库体积 2,601 MB vs 1,628 MB —— 物理碎片，不是数据差异
行数逐表一致（§2）。`account_move_line` 侧：现网 `pg_total_relation_size` 691 MB，恢复库 413 MB；
现网 `pg_stat_user_tables.n_live_tup` 显示 186（明显过期）而恢复库 818,693。
→ 现网该表存在大量未回收空间（9 月一次 383,989 行的大导入）。**不在 A1 处置**，记为 A2/B3 前的独立议题（VACUUM/REINDEX 需另评估，属写库动作）。

### 4.4 Odoo 19 登录表单口令字段是 `password`，不是 `passwd`
`POST /web/login` 带 `passwd=…` 会被静默忽略 → 恒返回 `Wrong login/password`（HTTP 200）。
A0 §结论表 ② 当时用这条判据得出"登录正常"，实际只证明了 CSRF 通道（真 token→200、假 token→400），**已在 A0 报告就地校订**。
所有历史/自动化脚本（含 `d-交付验收/uat_*.py`、`e2e_*.py`）沿用 `passwd` 的都需核一遍。

## 5. 登录/权限链路（HTTP 实测，平桥）

```bash
R="--resolve tour-staging.solepro.cloud:443:127.0.0.1"; B="https://tour-staging.solepro.cloud"
```

| 判据 | 内部用户 | 门户用户 |
|---|---|---|
| `GET /web/login` | 200，下发 `session_id` cookie（A0 废止 `X-Odoo-Database` 后无回归） | 同 |
| 真 `csrf_token` POST | 200→**303 → `/odoo`** | 303 → `/my` |
| 乱填 `csrf_token` POST | **400** | 400 |
| `GET /web`（带会话） | **200**（后端界面标记命中） | **303 → `/my`**（后台被拒） |
| `GET /my` | 200 | 200 |

→ 认证、会话、CSRF、权限边界（内部可达后台 / 门户被挡在 `/my`）四项在平桥上与预期一致。
